SECTION 01

What the portal is

The UPT Portal is a private document library for union members. It replaces the mix of WhatsApp threads and shared Google Drive folders that UPT used before. Members sign in with an email address, and each member sees only the documents their access level allows.

What it does today

  • Members read documents. After signing in, a member sees a single list of every document they are allowed to see, filterable by category and committee room.
  • Committee members add documents. Either by uploading a file (Word, PDF, anything) or by writing a page directly in the portal with a built-in editor.
  • Access is enforced on the server. A document is served only after the server checks the signed-in member's access level. A restricted document cannot be reached by guessing or sharing its web address.
  • Nothing is overwritten. Replacing a file or saving an edited page creates a new version, and the old one stays downloadable from the document's history.
  • Documents have a lifecycle. Draft, published, archived. Only published documents are visible to ordinary members.

What it deliberately does not do

  • No automatic import or sync from Google Drive. Existing documents are added by hand through the upload form.
  • No folders inside a committee room. Documents are organised by category tags, not a folder tree.
  • No project management, tasks, messaging or notifications. Those were scoped as later phases and have not been built.
  • No public pages. Every page requires a signed-in account.

How the pieces fit together

Member's browserAny modern browser, phone or desktop
signs in, requests pages
The portal applicationNext.js, hosted on Vercel
SuperTokensAccounts, passwords, sessions, roles
DynamoDBDocument records, rooms, categories

Files are the exception to the flow above: when someone uploads or downloads a file, the browser talks to S3 directly using a temporary signed link that the application issues after it has checked permissions. Large files never pass through the application server. The application also sends account emails (verification, password reset) through Gmail's SMTP service.

SECTION 02

Roles, ranks and committee rooms

This is the most important section for anyone operating the portal. Almost every "why can't this person see or do X" question is answered here.

The four access levels

Every member has exactly one role. The role gives them a rank, a number from 1 to 4. Every document has a minimum rank. A member can see a document when their rank is equal to or higher than the document's minimum rank.

RankName shown in the portalStored name (in code and data)Can do
1 General Member general Read documents at level 1. Cannot add or change anything, in any room.
2 Committee Member contributor Read levels 1 and 2. Can add and edit documents, but only inside committee rooms they belong to.
3 Committee Chair committee_chair Read levels 1 to 3. Adds and edits within their rooms, manages who is in those rooms, and can change other members' roles below their own level.
4 Super User committee_head Reads everything. Writes in every room. Creates committee rooms. Permanently deletes documents. The administrator role.
Naming trap

The names stored in the system are not the names shown on screen. contributor means "Committee Member" and committee_head means "Super User". These older names were kept so that live member records did not have to be rewritten. When using a command line tool or reading data directly, you must use the stored name. When talking to a member, use the display name.

The rule that explains everything: rooms control writing, not reading

A committee room is a container for a committee's documents, for example Housing, Legal, Outreach. It answers one question only: who is allowed to add or change documents here?

  • Reading is global. A member sees every document at or below their rank, in every room, whether or not they belong to that room. Rooms do not hide anything from anyone.
  • Writing is room-scoped. To add or edit a document in the Housing room, you must be a member of the Housing room (or a Super User, who can write anywhere).

This was a deliberate choice. If you need a document to be visible to fewer people, raise its access level. Moving it to a different room will not hide it.

Unfiled documents

A document does not have to belong to a room. Documents created before rooms existed have no room, and Super Users can deliberately leave a document unfiled. Only Super Users can edit an unfiled document. This is also how the very first document gets uploaded, before any room exists.

Two limits on role changes

  • Nobody can promote another member above their own rank.
  • A Super User's role can only be changed by that Super User themselves. This prevents two administrators locking each other out.
Remember

A member's role is copied into their sign-in session when they log in. After you change someone's role, they must sign out and sign back in before the change takes effect. This catches people out constantly.

Networking

There is none to manage. There is no VPC, no load balancer, no server and no fixed IP address. The application reaches DynamoDB and S3 over the public AWS API endpoints, authenticated with the upt-portal-app access key. This is why the infrastructure is small enough to describe on one page.

How access to the data is controlled

  1. The S3 bucket blocks all public access. There is no way to reach a file by URL alone.
  2. When a member downloads a document, the application checks their permissions and then generates a signed link that expires after 5 minutes.
  3. The application's AWS user can only touch the one table and the one bucket. If its key leaked, the damage is limited to portal data, and the key cannot delete files.

Cost

At this size the AWS cost is small: on-demand DynamoDB with 45 items and a few megabytes of S3 storage will be a few dollars a month at most. Vercel and SuperTokens may have their own plans. To confirm Current monthly spend across AWS, Vercel and SuperTokens, and which of these are on paid plans.

The single index, by-rank, is keyed on the document's minimum rank and last-updated time. It is what makes the filtered document list a small set of queries rather than a full table scan.

Note that member accounts and roles live in SuperTokens, not in this table. The USER# records here carry room memberships.

The flows worth understanding

Uploading a file (two steps, on purpose)

  1. The browser asks the application for an upload link. The application generates a new document id, works out where the file will live in S3, and returns a signed link valid for 5 minutes.
  2. The browser uploads the file straight to S3. The file never passes through the application server, so large uploads do not hit hosting limits.
  3. The browser then posts the document's details. The server re-derives the storage location from the id and filename rather than trusting the browser, so nobody can point a document record at somebody else's file.

If step 3 never happens (the member closes the tab), the uploaded file is orphaned in S3. No record references it and it is unreachable through the portal.

Downloading (the single enforcement point)

/api/documents/:id/download is where document access is decided. It checks the member's rank against the document's level, and hides drafts and archived documents from anyone who cannot manage the room. Anything the member is not allowed to see returns "not found" rather than "forbidden", so the endpoint never reveals that a restricted document exists.

Editing a page

Two separate mechanisms, often confused:

  • The edit lock is a courtesy. It tells a second editor that someone else is already in the document. It lasts 120 seconds and the editor renews it while you type. It is not a permission check and an expired lock never blocks a save.
  • The version check is the real protection. The editor sends the version number it loaded. If the document has moved on since, the save is refused with a conflict message rather than silently overwriting the other person's work.

Versions

Every replacement file and every page save becomes a new version with its own file in S3. Nothing is overwritten. One subtlety: version 1 has no stored record. A document that has never been replaced is its own version 1, described by the document record itself, and version 1 is written for real the first time someone replaces the file. Stored version numbers therefore start at 2.

Decisions worth knowing before changing anything

DecisionReason
Rooms scope writing, never readingKeeps the read path and its index unchanged, and keeps visibility governed by one number instead of two systems that can disagree.
Unauthorised requests return 404, not 403A 403 confirms the document exists. A 404 tells the caller nothing.
Page content is stored in S3, not in the database recordThe document list returns whole records. A body stored on the record would make every dashboard load fetch the full text of every visible document, and would hit DynamoDB's 400 KB item limit.
Deleting a document leaves the file in S3The application has no delete permission on the bucket. The record is gone and nothing references the file, so it is orphaned rather than exposed. Removing the bytes needs an infrastructure change.
A document cannot be moved between roomsMoving a document changes who can write it. Allowing it in the edit form would let a Chair walk a document into a room they control and take ownership of it.
Category identity ignores case and spacingStops "Minutes", "minutes" and " Minutes " becoming three categories. The first spelling wins.
The S3 client sets requestChecksumCalculation: "WHEN_REQUIRED"Without it, the AWS SDK bakes a checksum of an empty body into signed upload links and S3 rejects the real file. Do not remove this line.
The document list queries once per rank and merges in memorySimple and correct at this size. It will need pagination well before the library reaches thousands of documents.
SECTION 05

Infrastructure implementation

The AWS resources are defined in code using AWS CDK (TypeScript) in the infra/ folder, and created through CloudFormation. Nothing was clicked together by hand in the console, and nothing should be: a manual change will be reverted the next time someone deploys.

The three stacks

StackFileCreates
UptPortalStorageStackinfra/lib/storage-stack.tsThe private S3 bucket, with public access blocked, encryption, versioning and browser upload CORS.
UptPortalDataStackinfra/lib/data-stack.tsThe DynamoDB table, its by-rank index, automatic expiry and point-in-time recovery.
UptPortalAccessStackinfra/lib/access-stack.tsThe upt-portal-app IAM user and its permissions.

Four things to know

  1. The bucket and table are set to be retained. Deleting a stack leaves them, and their contents, in place. This is deliberate protection against an accidental teardown.
  2. Names are fixed in code. The table and bucket are named explicitly so that a CDK version upgrade can never trigger a replacement, which would silently drop all data.
  3. The access stack refers to the table and bucket by name, not by cross-stack reference. Deploy it after the other two exist. cdk deploy --all handles the order.
  4. No access key is created by CDK. If it were, the secret would end up in CloudFormation state. It is created by hand once, after deployment, and stored in the application's environment.

Tests

infra/test/ contains 13 assertion tests covering the security-relevant settings: public access blocked, encryption and versioning on, retention policies, the table's keys, index, expiry and backups, the application user's permissions (including that it has no delete on the bucket), and that no access key is created. Run them with npm test in infra/, and before every infrastructure deployment.

SECTION 06

Deployment and release

There are two independent deployment paths. Application changes and infrastructure changes are deployed separately, and most releases only involve the application.

Application: push to GitHub, Vercel builds and deploys

Confirm before relying on this

The repository and configuration make clear the application is hosted on Vercel and deployed from Git. To confirm the Vercel account or team that owns the project, the project name, the production domain, and which branch is set as production (assumed to be main).

Prerequisites

  • Write access to github.com/union-of-pinnacle-portal/upt-portal.
  • Node.js and npm installed locally.
  • Access to the Vercel project to view build logs and environment variables.

Steps

  1. Work on a branch, never directly on main.
    git checkout -b feat/short-description
  2. Check the build passes locally before pushing. This is the only gate that exists, so do not skip it.
    cd app
npm install     # first time, or after dependency changes
npm run lint
npm run build
  3. Test the change against the real data stores by running the app locally. This uses the same AWS table and bucket as production, so avoid creating test documents you will not clean up.
    npm run dev     # http://localhost:3000
  4. Push the branch and open a pull request. Vercel builds a preview deployment for it, with its own temporary URL. Check the change there.
    git push -u origin feat/short-description
  5. Merge the pull request into main. Vercel builds and deploys production automatically.
  6. Verify the deployment.
    Expected result: the Vercel dashboard shows the deployment as Ready; loading the portal signs you in as normal; the dashboard lists documents without an error banner; opening one document downloads or renders it.

If a deployment goes wrong

In the Vercel dashboard, open Deployments, find the last known good one, and use "Promote to Production" (older Vercel versions call this Rollback). This takes effect in seconds and does not require a code change. Then fix the problem properly on a branch.

Infrastructure: deploy from a developer's machine

There is no automation for this. Infrastructure changes are rare and are deployed by hand from the infra/ folder using the upt-portal AWS profile.

  1. Make sure your AWS profile works and points at the right account.
    aws sts get-caller-identity --profile upt-portal
    Expected result: account 444655872449, user upt-admin.
  2. Install dependencies and run the infrastructure tests.
    cd infra
npm install
npm test
  3. Review exactly what will change. Read this output carefully. Anything that says "destroy" or "replace" on the table or bucket must be stopped and investigated.
    AWS_PROFILE=upt-portal npx cdk diff --all
  4. Deploy.
    AWS_PROFILE=upt-portal npx cdk deploy --all
  5. Verify.
    Expected result: CDK reports each stack as deployed with no errors, and the portal still lists and opens documents.
Never do this

Do not run cdk destroy. The bucket and table are set to be retained so the data would survive, but the application's IAM user would be deleted and the portal would immediately lose all access to its data.

One-time setup, for reference

These steps have already been done. They are recorded here in case the portal is ever rebuilt.

# Once per AWS account and region
AWS_PROFILE=upt-portal npx cdk bootstrap

# After the first deploy: create the application's access key.
# The secret is shown only once. Put it straight into Vercel's environment variables.
aws iam create-access-key --user-name upt-portal-app --profile upt-portal
SECTION 07

Day-to-day operations

These are the tasks the UPT team will actually do. Each one says who can do it, where, and what you should see when it has worked. None of them require a developer.

7.1 Give a new person access to the portal

Anyone can registerRole set by rank 3+

New members create their own account. An administrator then sets what they can see.

  1. Send them the portal address and ask them to choose Register, or to sign in with Google.
  2. They receive a verification email and must click the link in it. They cannot sign in until they do. If it does not arrive, see section 8.
  3. Once they have signed in at least once, open the account menu (the circle with initials, top right) and choose Manage members.
  4. Find their email in the list and set their role. New accounts start as General Member.
  5. If they need to add or edit documents, add them to a committee room as well (7.4).
  6. Tell them to sign out and back in.
    Expected result: after signing back in, the account menu shows their new role, and they can see the documents for that level.

7.2 Change someone's role

Committee Chair and above/admin/users
  1. Account menu, top right, then Manage members.
  2. Find the person and pick the new role. Chairs see only members of their own rooms; Super Users see everyone.
  3. Ask them to sign out and sign back in.
    Expected result: the list shows the new role immediately. What the member can actually see changes only after they sign in again.

You cannot promote anyone above your own level, and a Super User's role can only be changed by that Super User.

7.3 Create a committee room

Super User only/rooms
  1. Go to Committee rooms from the dashboard header.
  2. Choose Create room, give it a name (up to 100 characters) and an optional description.
  3. Add the committee's members (7.4).
    Expected result: the room appears in the list with a member count, and it becomes selectable in the "Add document" form for its members.

Remember that a room does not hide anything. It decides who can add and edit, not who can read.

7.4 Add or remove someone in a committee room

Chair of that room, or any Super User
  1. Open Committee rooms and click into the room.
  2. Enter the person's email address to add them, or use the remove control next to an existing member.
  3. The email must already have a portal account. If it does not, you will see "No portal account exists with that email". Ask them to register first (7.1).
    Expected result: the person appears in the room's member list and can immediately add documents to that room, without signing out and in.

7.5 Add a document

Room members, rank 3+ in the current interface

Two kinds. Upload a file when you have an existing document. Create a page when you are writing something new that people may edit later.

  1. On the dashboard, choose Add document, then either Upload file or Create page.
  2. Fill in the title, an optional description, and one or more categories. You can type a new category name and create it on the spot.
  3. Choose the committee room. Super Users may leave it unfiled.
  4. Choose who can view. This is the access level and it is the only thing that restricts visibility:
    • All members (general and up)
    • Committee members and up
    • Committee chairs and up
    • Super users only
  5. Choose draft or published. Drafts are visible only to people who can manage the room.
  6. Save.
    Expected result: the document appears at the top of the dashboard list. Uploaded files download when clicked; pages open in the editor.

7.6 Publish, unpublish or archive a document

Write access to the document's room
  1. Find the document on the dashboard and open its actions menu, or open the document and choose Edit details.
  2. Change the status:
    • Published makes it visible to everyone at or above its access level.
    • Draft hides it from ordinary members while you work on it.
    • Archived retires it. It stays in the system and stays visible to room managers, but ordinary members no longer see it.
  3. Save.
    Expected result: the status shown on the dashboard row changes, and the document disappears from ordinary members' lists if you moved it out of Published.

Archive is the right tool for anything that is a real record. It is reversible. Deleting is not.

7.7 Replace a file with a newer version

Write access to the document's room
  1. Open the document's actions and choose to replace the file.
  2. Pick the new file. It uploads directly and becomes the current version.
  3. Check the version history.
    Expected result: the new version is listed at the top with your name and the time, and every earlier version is still listed and still downloadable. Nothing is overwritten.

7.8 Turn an uploaded Word document into an editable page

Write access to the document's room

Useful when a .docx needs to become something people maintain in the portal instead of by emailing files around.

  1. Open the document and choose the convert action.
  2. The conversion happens in your browser and is saved as a new version.
  3. Check the result. Complex formatting (tables, columns, embedded images) may not survive cleanly.
    Expected result: the document now opens in the editor. The original Word file is still in the version history and can still be downloaded, so a poor conversion is recoverable.

7.9 Permanently delete a document

Super User onlyNot reversible
Use archive instead, unless this is junk

Delete removes the document record and its entire version history. There is no undo in the portal. It exists for test uploads, wrong files and duplicates. For anything that is a real union record, archive it.

  1. Open the document's actions menu and choose Delete.
  2. Confirm.
    Expected result: the document disappears from every list. The underlying file remains in S3 but is unreachable through the portal, and a developer can recover it from the bucket if you act quickly and know the document's id.

7.10 Create the first Super User (or recover when there is none)

Needs the admin code, or developer access

There are two ways. The first needs no developer.

Using the admin code at registration

  1. On the registration page, enter the admin code in the optional field alongside the email and password. The code is the ADMIN_BOOTSTRAP_SECRET value set in the Vercel environment.
  2. Complete registration and verify the email address.
  3. Sign in.
    Expected result: the account menu shows "Super User" and the Committee rooms and Manage members options are available.
Treat this code like a password

Anyone who has it can make themselves an administrator. Share it only when creating an administrator, and change it in Vercel afterwards if it has been circulated.

Using the command line (developer)

cd app
npm run set-role -- someone@example.com committee_head

This requires app/.env.local to be set up with the SuperTokens connection details. Use the stored role names: general, contributor, committee_chair, committee_head. The person must sign out and back in.

7.11 Two maintenance scripts you may need

Developer, and see the caveat
These are not wired up

Both scripts exist in app/scripts/ and their documentation refers to npm run seed-categories and npm run migrate-minrank, but neither entry exists in app/package.json. Until someone adds them, run them directly:

SECTION 08

Monitoring and troubleshooting

Current state

There is no monitoring configured. No CloudWatch alarms exist in the AWS account, no error tracking service is connected, and nothing will notify anyone if the portal breaks. In practice you will find out when a member reports it. Adding alarms is the highest-value operational improvement available and is listed in section 11.

Where to look

QuestionWhereWhat you get
Is the site up? Did the last deploy work? Are there server errors? Vercel dashboard, Deployments and Logs Build output, runtime logs including any error thrown by an API route. This is the first place to look for almost everything.
Can people sign in? Does an account exist? SuperTokens dashboard URL to confirm The user list, sign-in methods, and whether an email is verified.
Is a document record correct? AWS console, DynamoDB, table upt-portal, Explore items The raw records. Read them freely; edit them only as a last resort.
Is a file actually stored? AWS console, S3, bucket upt-portal-documents Objects under documents/<document id>/ and pages/<document id>/.
Is AWS itself throttling or erroring? AWS console, CloudWatch, Metrics, DynamoDB and S3 Request counts, throttled requests, error rates. On-demand billing makes throttling unlikely at this size.
What changed recently? GitHub commit history on main Correlate a new problem with the deployment that introduced it.

Common problems

SymptomMost likely causeWhat to do
"I registered but I cannot sign in" Email address not verified. Verification is required. Ask them to check spam and junk for a mail from the portal. They can trigger a new one from the verify-email page. If nothing arrives, see the email row below.
No emails arriving at all (verification, password reset) The Gmail app password has been revoked or the sending account has a problem. All portal email goes through one Gmail account over SMTP. Check the Vercel logs for SMTP errors. Confirm the app password is still valid in the Google account's security settings, and update GMAIL_APP_PASSWORD in Vercel if it was regenerated. Redeploy after changing it.
"I was made a Chair but nothing changed" The role is copied into the session at sign-in. Sign out fully and sign back in. Confirm the role in the account menu.
"I cannot add a document to a room" Not a member of that room, or the interface only offers the button to rank 3 and above. Add them to the room (7.4). If they are a Committee Member and still see no Add button, this is the known interface limit in section 12.
A document link gives "not found" for one person but works for another Working as designed. Their rank is below the document's access level, or the document is a draft or archived and they cannot manage its room. Check the document's "who can view" setting and status. Raise their role or lower the document's level if appropriate.
Upload fails part way, or the file never appears The signed upload link expired (5 minutes), the connection dropped, or the browser tab was closed between uploading and saving. Try again. Large files over slow connections are the usual cause. If it repeats, check the browser console and Vercel logs for the exact error.
"Someone else is editing this document" Another person holds the advisory edit lease, or held it within the last two minutes. Wait two minutes and reload. The lease expires on its own; nobody can be permanently locked out.
"This document changed while you were editing it" Someone saved a newer version after you opened yours. The save was refused rather than overwriting them. Copy your text out of the editor first, then reload the page and reapply your changes. Your text stays in the editor until you leave the page.
The dashboard shows an error banner instead of documents DynamoDB is unreachable: expired or deleted AWS key, wrong region, or an AWS incident. Check the Vercel logs for the AWS error. Confirm the upt-portal-app access key is still Active in IAM and that the four AWS environment variables in Vercel are correct.
The category picker is empty No categories have been created yet. Anyone who can upload can type a new category name and create it inline, or run the seeding script (7.11).
A document's room shows as "Unknown room" The room record no longer exists but the document still points at it. The document is still readable. Only a Super User can edit it. Recreating a room does not restore the link, because rooms are identified by a generated id.

When something is broken and you do not know why

  1. Establish the blast radius. Is it one member, one document, or everybody? One person usually means permissions or session; everybody usually means a deployment or a service.
  2. Open the Vercel dashboard. Check whether the most recent deployment succeeded and look at the runtime logs for errors around the time of the report.
  3. If the last deployment is the suspect, promote the previous good deployment back to production (section 6). Restoring service comes before diagnosis.
  4. If sign-in is failing for everyone, check SuperTokens. If documents are failing for everyone, check the AWS key and the AWS status page.
  5. Write down what you found. This document should grow a new row in the table above each time.

Rotating the application's AWS key

Do this in order. Done this way there is no downtime, because both keys are valid in the middle.

  1. Create a second key for the same user. 
    aws iam create-access-key --user-name upt-portal-app --profile upt-portal
    Expected result: a new key id and secret, shown once. Copy both immediately.
  2. Update AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY in Vercel's environment variables.
  3. Redeploy the application so the new values are picked up.
  4. Confirm the portal still lists and downloads documents.
    Expected result: the dashboard loads with no error banner and a document opens.
  5. Only then, delete the old key. 
    aws iam list-access-keys --user-name upt-portal-app --profile upt-portal
aws iam delete-access-key --user-name upt-portal-app --access-key-id <OLD_KEY_ID> --profile upt-portal
  6. Update app/.env.local on any developer machine that uses the old key.

SECTION 12

Known limitations and considerations

These are real and current. None of them are blocking day-to-day use, but each is worth knowing before it surprises someone.

Security and access

IssueImpactSuggested response
The admin code endpoint is unauthenticated. /api/auth/set-admin-role accepts a user id and the bootstrap code, with no sign-in required and no rate limiting. Anyone who learns the code can promote an account to Super User. Repeated guessing is not blocked. Treat the code as a high-value secret, change it after each use, and consider removing the endpoint once the administrators exist.
Role changes are limited by rank but not by room. A Committee Chair can change the role of any member below rank 3, not only members of their own rooms. A Chair can promote someone outside their committee to Committee Member. The member list they see is room-scoped, so this needs a deliberate direct API call rather than a click. Scope the role change endpoint by room membership for Chairs.
One shared AWS administrator user with a long-lived access key. No individual accountability, and rotation affects everyone at once. Individual IAM users with multi-factor authentication.
Portal email is sent from a personal Gmail account using an app password. Sign-up and password reset stop working if that account changes its security settings or is lost. Gmail also has daily sending limits. Move to a union-owned account or an email sending service.
The route middleware only checks for a cookie, only on /dashboard. No impact today, because every page and route enforces permissions itself. The risk is a future route that assumes middleware is protecting it. Keep calling getCurrentUser() and the permission checks in every new route.

Functional gaps

  • Committee Members cannot see the Add document button. The permission rules allow rank 2 to add documents in their rooms, but the dashboard only shows the button to rank 3 and above. Either the rule or the interface should change; today the effective answer is that Chairs and Super Users add documents.
  • Rooms cannot be renamed or deleted through the portal. There is no endpoint for it.
  • Documents cannot be moved between rooms. This was deliberate, but there is no Super User action to do it either, so a mis-filed document stays where it is.
  • Categories cannot be renamed, merged or deleted. They accumulate. A cleanup tool would have to rewrite every tagged document.
  • No account deletion in the portal. Removing a member entirely requires the SuperTokens dashboard.
  • Download activity is recorded but never shown. The data model has download log records; no screen displays them and nothing writes them today.
  • Word conversion is approximate. Tables, columns and embedded images may not survive. The original file is always kept in the version history.

Technical constraints

  • The document list does not paginate. It queries one partition per access level and merges the results in memory. Correct and fast at 5 documents; it will need rework in the hundreds to low thousands.
  • The member list is capped at 500 accounts, and builds the list by fetching each member's role one at a time. It will get slow well before that cap.
  • Deleted documents leave their files behind in S3, because the application has no delete permission on the bucket.
  • Access level 3 changed meaning when Committee Chair was added. Run the migration script before appointing the first Chair (7.11). There are currently no documents at that level, so nothing is at risk today.
  • The only automated tests are for infrastructure. There are 13 CDK assertion tests and no tests for the application, including none for the permission logic, which is the part most worth testing.
  • No continuous integration. Nothing runs the build or the tests automatically. A broken build is caught by Vercel at deploy time; a broken permission rule is caught by a person.
  • One environment. There is no staging. Local development runs against live data, and preview deployments do too.

Assumptions the design rests on

  • A small union: dozens of members, a handful of committees, hundreds of documents at most.
  • Members are trusted colleagues, not adversaries. The access levels stop accidental oversharing, not a determined attacker with an account.
  • Volunteers operate the portal, so a task that needs a developer is a task that may not get done. Anything routine should be doable through the interface.
